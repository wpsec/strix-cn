## Token 限制下的渗透测试计划（已实施）

### 核心原则

配置了扫描 Token 限制时，不平均分配 Token，不以低危覆盖面优先；必须在有效 Token 内优先完成严重和高危漏洞的发现、验证、复测与报告，再扩展中低危测试。Token 不足时应明确标记未覆盖范围，不能将扫描报告标记为完整或无风险。

### 配置与用量定义

- 新增独立配置 `token_limit`，避免与现有费用预算 `max_budget_usd`、单次请求 `max_tokens` 混淆。
- `token_limit` 为空或未配置时不限制扫描 Token，但仍记录实际用量。
- 配置后必须为正整数；无效值、零值和负值直接拒绝。
- 有效 Token 按模型调用的 `input_tokens + output_tokens` 统计；供应商未返回用量时使用保守估算，不能按零 Token 处理。
- `max_budget_usd` 与 `token_limit` 同时配置时，任一限制先达到即停止继续扩展测试。

### 测试计划与调度规则

扫描启动后先生成任务清单。每个任务至少记录风险等级、目标、测试类型、预计 Token 和是否强制执行，并按以下优先级调度：

- P0：授权与范围确认、攻击面识别、认证与授权检查、严重和高危漏洞路径。
- P1：P0 发现的验证、复测、影响确认和漏洞报告。
- P2：中危漏洞及其扩展测试。
- P3：低危、边缘场景和广度型探索。

调度规则如下：

- 预留 20% Token 用于严重/高危漏洞验证、复测和最终报告；预留部分不能被普通低优先级任务消耗。
- 创建新测试任务前，检查“已用 Token + 任务预计 Token + 报告预留”是否超过限制；不足时跳过低优先级任务。
- Token 很少时，只执行 P0 中风险最高、最可能产生严重影响的任务；不能为了扩大覆盖面牺牲高危路径验证。
- 达到限制后停止创建新任务，收束当前可完成的验证和报告，并将运行状态标记为 `token_limit_exhausted`。
- Token 耗尽的运行必须在报告中列出已完成测试、未完成阶段、跳过任务和严重度覆盖情况，不能报告为“扫描完成”或“未发现问题”。

### 持久化、恢复与验收

运行记录增加以下信息：

- `token_limit`
- `tokens_used`
- `tokens_remaining`
- `token_limit_status`
- `completed_priorities`
- `skipped_tasks`
- `coverage_by_severity`
- `stop_reason`

恢复扫描默认沿用原始 Token 限制和未完成任务计划；只有显式提供更大的 `--token-limit` 总上限时才追加额度，已消耗 Token 不重置，未显式追加额度时不得重新获得完整 Token 配额。

实现验收至少覆盖以下场景：

- 空限制时不触发 Token 调度拦截。
- 有限 Token 时严重/高危任务始终先于中低危任务。
- Token 不足时低优先级任务被跳过。
- 预留 Token 不会被普通任务耗尽。
- 实际用量缺失时采用保守估算。
- Token 耗尽后报告状态为不完整，并准确展示未覆盖范围。
- 恢复扫描不会重复分配已消耗的 Token。

### 假设与边界

- “有效 Token”指扫描级模型输入与输出 Token 总量，不指模型上下文窗口，也不指单次响应输出上限。
- 现有 `max_budget_usd` 继续负责费用限制，不改为 Token 限制。
- 本节作为 CLI 配置、优先级调度器、运行记录、报告边界和回归测试的实现与验收依据。

### 发现项

#### [important] bind-mount 启动前异常会遗留包含用户文件的临时目录

- 位置：`strix/runtime/session_manager.py:634-672`、`518-562`、`689-749`
- 当 runtime 使用 bind-mount backend 且存在 `extra_files` 时，`extra_file_staging_dir()` 会先创建 `/tmp/strix-extra-files-*` 并把文件内容写入其中。可是 `build_extra_file_bind_mounts()`、`Manifest(...)` 和 `_assert_burp_port_available()` 都发生在 `try`（第 689 行）之前；这些步骤任一失败时，第 739-749 行的清理分支不会执行，`cleanup(scan_id)` 也找不到尚未缓存的 bundle。
- 影响：端口冲突、manifest 构造失败或写入异常可能让用户提供的 workspace 文件长期留在宿主机临时目录；其中可能包含 API 规范、字典或其他敏感辅助材料。
- 建议：把 staging 创建及所有启动前置步骤纳入统一的 `try/finally`，或在创建 staging 后立即注册可独立回收的清理句柄；补充“preflight 抛错后目录不存在”的测试。
- 处置：已将 staging、Manifest 构造和端口预检纳入统一清理路径；`test_create_or_reuse_removes_staging_when_preflight_fails` 已覆盖异常回收。

#### [important] Windows drive letter 被误解析为 `PATH[:DEST]` 的分隔符

- 位置：`strix/interface/utils.py:1917-1920`、`1949-1953`
- `resolve_workspace_files()` 和 `_workspace_file_dest()` 直接对 spec 使用 `rpartition(":")`。在 Windows 上，`C:\\wordlist.txt` 会被拆成 source=`C`、dest=`\\wordlist.txt`，随后报“不是现有文件”；未显式指定目标路径的绝对 Windows 文件因此无法使用 `--workspace-file`。
- 影响：与文档声明的 Windows 兼容性不一致，且当前测试只覆盖 POSIX 路径。
- 建议：解析时先用 `os.path.splitdrive()`/平台路径规则识别 drive prefix，仅把 drive prefix 之后的冒号或明确的 `:DEST` 视为目标分隔符；补充 Windows 风格路径回归测试。
- 处置：新增跨平台 `PATH[:DEST]` 拆分 helper，使用 Windows 路径规则识别 drive prefix；`test_a_windows_drive_letter_is_not_a_destination_separator` 已覆盖无目标和显式目标两种形式。

#### [important] 公开 `--host` 后 Viewer 的 POST body 没有大小上限

- 位置：`strix/interface/viewer/cli.py:48-52`、`strix/interface/viewer/server.py:262-295`
- 本次合并把 `--host` 从隐藏参数改为公开参数，并明确支持 `0.0.0.0`。但 `_read_body()` 直接信任客户端 `Content-Length` 并执行 `rfile.read(length)`，未做上限、超时或过大请求拒绝；该入口还被 `/api/event`、反馈和认证 POST 路径复用。
- 影响：Viewer 被绑定到非本机接口时，未认证网络客户端可以发送超大 body 或长时间维持声明长度的请求，消耗线程、内存和可用性。session cookie 能保护报告数据，但不能解决这个资源消耗面。
- 建议：统一设置较小的 JSON body 上限，先校验并拒绝过大的 `Content-Length`，同时对非法值返回 4xx；为 `--host 0.0.0.0` 增加远程请求体/超时测试。
