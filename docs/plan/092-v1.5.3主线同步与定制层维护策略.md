# 092 `v1.5.3` 最新同步与定制层维护策略

## 摘要

本文档记录截至 `2026-08-14` 的最新一轮上游同步判断。目标不是证明“能不能合”，而是给 `strix-cn` 维护者一份可以直接执行的决策单，回答下面三个问题：

- 这次能否更新到最新上游，同时保住 `strix-cn` 既有能力
- 哪些上游提交和文件应该收，哪些必须手工合，哪些本轮先不跟
- 合并后哪些现有功能会受影响，应该如何验证和止损

本轮结论是：**可以追到最新上游，但不建议直接把 `upstream/main` 整包 merge 到 `main`。** 推荐采用“上游主线层 + `strix-cn` 定制层”的分层吸收策略：通用修复优先吸收，高风险热点文件只做人工片段整合。

## 背景与结论

### 本轮基线

- 评估日期：`2026-08-14`
- 当前维护线：`main`
- 当前上游线：`upstream/main@8ca0c4a9`
- 上游发布时间点：`v1.5.3`
- 公共基线：`597aae6 (v1.5.2)`

### 分叉规模

- `main` 相对公共基线领先 `33` 个提交
- `upstream/main` 相对公共基线领先 `9` 个提交
- Git 预合并结果：**无文本冲突**
- 同时存在双方改动的重叠文件：`10` 个
- 相对当前 `main`，吸收本轮上游后会新增或变更的文件：`17` 个

### 结论

- 这轮上游不是 TUI、Viewer、Runtime 的架构级重构，主要是浏览器容器、LLM 请求构造、OpenRouter attribution 和 LiteLLM 成本解析修复
- 这类修复总体属于 `strix-cn` 应当跟进的上游通用能力，长期维护收益高于成本
- 风险主要集中在本分支已经长期维护的热点文件，而不是整仓库
- 因此，本轮适合采用“挑高价值提交吸收 + 高风险文件人工整合 + 最小回归验证”的方式推进，而不是直接整包 merge

## 冲突与影响分层

### Git 事实

- 预合并命令显示：当前 `main` 合 `upstream/main` 时没有文本级冲突
- 同时被两边修改的文件有 `10` 个，但全部可以自动合并
- 自动合并不等于无风险。风险主要来自“同一热点文件里，本地长期定制能力是否被语义回退”

### 直接收

这类改动维护收益高，且不要求我们长期背新的产品面：

- LLM 请求构造与 provider 兼容修复
- OpenRouter attribution 请求级修复
- LiteLLM 成本估算与 observed cost 优先级修复
- 对应的 focused tests 与成本统计测试

对应范围以行为分类为主：

- `make_model_settings` 相关逻辑
- tool-less request 调用点
- `LLMUsageLedger` / pricing 辅助逻辑
- `tests/test_inputs.py`、`tests/test_cost_tracking.py`、`tests/test_pricing.py`

### 收但必须手工整合

这类文件属于 `strix-cn` 已经深度定制的高风险热点，即使 Git 能自动合，也不能无脑接受结果：

- `containers/Dockerfile`
- `strix/agents/prompts/system_prompt.jinja`
- `strix/report/state.py`

手工整合的原则：

- `Dockerfile`：保留本分支的镜像源、代理、国内网络兼容与本地构建适配，同时吸收 browser session 生命周期修复
- `system_prompt.jinja`：保留中文默认体验、被动代理约束、凭据约束和 workspace 编辑边界，只摘取上游新增的 browser session 规则
- `report/state.py`：保留本分支的代理元数据、HTML 交付、`validation_evidence`、报告扩展字段，只引入成本估算修复相关片段

### 低价值可延后

这类内容本身不值得单独为它们扩大冲突面：

- `7cc9fa9f`：release bump
- `372e27fa`、`ae07af61`：注释清理
- 纯 lockfile 漂移

这类提交不需要为了“追最新”而单独追入。只要有价值修复已经被吸收，版本号和注释类差异可以延后统一处理。

### 本轮不收

本轮评估范围内，**没有发现必须明确拒收、否则会把不属于 `strix-cn` 长期维护面的能力带进来的改动**。  
本轮的重点不是“拒绝某个新能力”，而是“避免用错误方式把正确修复吸收成高维护成本”。

## 本轮执行策略

### 默认策略

不建议直接执行：

```bash
git merge upstream/main
```

推荐策略：

1. 在临时同步分支预演，不污染维护线
2. 优先吸收高价值通用修复提交
3. 对高风险热点文件做人工片段整合
4. 完成最小回归后，再决定是否把同步分支合回 `main`

### 关键提交处理方式

| 提交 | 建议处理 |
|---|---|
| `649a2e21` | 建议收。属于典型 provider 兼容修复，收益高，维护成本低 |
| `174c16fa` | 建议收。属于 OpenRouter 请求级一致性修复，应作为通用兼容能力吸收 |
| `7b3c8f9b` / `ad727edd` / `94a2586a` | 建议收，但 `containers/Dockerfile` 必须人工整合，不能整文件选边 |
| `8ca0c4a9` | 建议收，但 `strix/report/state.py` 需人工核对本地扩展字段和成本写入链路 |
| `7cc9fa9f` | 可延后，不值得单独为 release bump 扩大同步面 |
| `372e27fa` / `ae07af61` | 可延后，不值得单独同步注释清理 |

### 本轮推荐处理顺序

1. 先吸收 `649a2e21` 与 `174c16fa`
2. 再处理浏览器容器修复组
3. 最后吸收 `8ca0c4a9` 成本统计修复
4. 所有高风险文件合并完后，再统一跑最小验证集

这样排序的原因是：

- 先解决请求构造和 provider 兼容，能尽早排除预热路径回归
- 浏览器容器修复与本地镜像兼容冲突最重，单独处理更清晰
- `report/state.py` 的人工核对成本最高，放在最后更便于集中验证

## 本轮最小验证集

本轮是文档决策单，但后续执行同步时应至少验证下面项目。每项都要有明确目的，不能只机械跑测试名。

### Python focused tests

- `tests/test_inputs.py`
  - 目标：确认 prompt scope、proxy passive mode、credentials 注入、tool-less request 相关输入构造没有回退
- `tests/test_cost_tracking.py`
  - 目标：确认 streamed / estimated cost 回退问题修复后仍能覆盖现有模型路径
- `tests/test_pricing.py`
  - 目标：确认 provider-qualified model resolution 与 observed cost 优先策略成立
- `tests/test_report_state_proxy.py`
  - 目标：确认成本写入修复没有覆盖本地报告状态与代理元数据
- `tests/test_runner_root_prompt.py`
  - 目标：确认 root prompt 仍保留中文、被动代理、黑盒编辑边界等本地约束

### 冒烟验证

- 浏览器容器启动冒烟
  - 目标：确认 `agent-browser` idle timeout、env 持久化与 profile 写入路径同时成立，且不破坏本地镜像兼容能力
- OpenRouter 预热路径冒烟
  - 目标：确认 attribution headers 会随请求发送，且不只停留在全局默认值
- tool-less request 预热路径冒烟
  - 目标：确认 dedupe / compaction / preflight 等无工具请求不再携带不兼容的 `parallel_tool_calls`

## 下次复用规则

为了以后做到“尽量跟最新，但不冲掉本地价值”，同步前应固定执行下面四条短 SOP：

1. **同步对象优先按发布切片，其次才是 `upstream/main`。**  
   能用稳定 tag 或明确提交切片解决的问题，不要默认整包追主线。

2. **高风险文件默认人工审查。**  
   对 `containers/Dockerfile`、`system_prompt.jinja`、`report/state.py` 这类本地长期热点，Git 的 auto-merge 不能视为验收结果。

3. **同步判断单位从“仓库整体”改成“能力分层”。**  
   每次先问：这次影响的是中文体验、代理工作流、Docker 兼容、报告交付，还是 provider 兼容；不要只看“改了几个文件”。

4. **任何声称“必须保留”的本地能力，都必须能映射到 `091` 的能力契约或 focused test。**  
   没有契约或 guard test 的“本地习惯”，不应被提升成强制保留项。
