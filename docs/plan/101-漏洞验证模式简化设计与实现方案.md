# 101 漏洞验证模式简化设计与实现方案

## 状态

已实现首版核心链路：请求解析、自然语言类型推断、验证计划确认、受限执行、证据持久化和修复复测比较。

## 目标

在现有普通扫描、红队专项模式和 Burp 被动扫描之外，增加一个面向单个漏洞案例的 `verify` 模式。使用者只需要提供：

1. 一个 Burp 请求包（Raw HTTP 或 Copy as cURL）。
2. 一句自然语言漏洞描述。

系统自动推断漏洞类型、可变异字段、低副作用探针和证据规则，并在发送请求前展示验证计划。

## 使用方式

交互模式：

```bash
strix --verify
```

交互流程：

1. 粘贴 Burp Raw HTTP 或 Copy as cURL 请求，以单独一行 `__STRIX_END__` 结束。
2. 输入一句问题描述，例如“疑似 IDOR，修改订单 ID 后可能读取其他用户订单”。
3. 查看 Strix 识别的漏洞类型、目标字段、验证动作、预计请求数和副作用提示。
4. 确认后执行；IDOR/BOLA 需要第二身份时，再粘贴第二个请求包。
5. 查看验证结论和报告路径。

自动化或非交互模式：

```bash
strix --verify --request ./burp-request.txt \
  --issue "疑似 IDOR，修改订单 ID 后可能读取其他用户订单" \
  -n --yes
```

修复后复测：

```bash
strix --verify --baseline <历史运行名> \
  --request ./burp-request-after-fix.txt -n --yes
```

请求包中的绝对 URL 会直接确定 Scheme。Raw 请求使用相对路径且没有 Scheme 时，交互模式只询问一次 `http` 或 `https`；非交互模式直接报错，避免把请求误发到错误协议。

## 输入和内部模型

首版不要求用户填写漏洞类型、参数路径、探针数量、计划哈希或结构化 JSON。内部将输入转换为：

```python
class VerificationCase:
    request: CanonicalRequest
    issue_description: str
    baseline_run: str | None
    supporting_requests: list[CanonicalRequest]
```

随后确定性生成 `VerificationPlan`，包含漏洞类型、目标字段、探针、断言所需响应摘要、请求上限、计划哈希和副作用约束。计划阶段不发送网络请求。

当前支持的类型识别和策略为：

| 类型 | 首版动作 | 安全限制 |
|------|----------|----------|
| SQL 注入 | 布尔真值/假值差异探针 | 不执行写入、删除和批量查询 |
| IDOR/BOLA | 使用第二请求中的测试对象标识 | 没有第二请求时阻断，不能报告为已确认 |
| 认证/授权绕过 | 移除认证信息后有限重放 | 只测试当前请求的认证边界 |
| SSRF | 使用描述中的受控 Canary URL | 拒绝本机、内网、云元数据和保留地址 |
| 命令注入 | 固定身份确认 marker | 不执行 Webshell、反弹 Shell 或持久化动作 |
| 文件上传 | 生成随机无害 marker | 没有可靠清理动作时默认阻断执行 |

请求默认保持原始 Host、Scheme 和 Port。第二身份请求也必须使用相同目标主机；不支持跨主机替换。

## 执行边界

所有验证请求由专用 `VerificationExecutor` 执行，不允许 Agent 直接调用 `curl`、Shell 网络命令或任意 MCP 请求。执行器保证：

- 只修改计划识别出的字段。
- 单次计划最多 20 个请求，并在计划中展示预计数量。
- 不自动跟随重定向。
- 不进行暴力破解、批量枚举或批量数据收集。
- POST、PUT、DELETE 等非幂等请求需要额外副作用确认。
- 缺少可靠清理动作的探针被阻断。
- 未确认计划时不调用网络执行器。

`--yes` 只在非交互模式可用，并视为对当前计划及其副作用提示的明确确认；目标范围、计划结构和请求上限仍由执行器强制约束。

## 修复复测和结果

每次验证保存到 `strix_runs/<run-name>/`：

```text
verification-plan.json
verification-result.json
verification-evidence.jsonl
penetration_test_report.md
run.json
```

复测时读取历史计划，校验计划哈希和新请求结构（方法、目标、字段集合和请求体结构一致，认证值和普通参数值可更新），再使用同一组探针和断言执行。结果规则：

- 基线确认、复测未复现：`fixed`
- 基线确认、复测仍复现：`still_vulnerable`
- 基线本身未复现：`inconclusive`
- 任一阶段证据不足：`inconclusive`
- 缺少第二身份：`needs_secondary_identity`

报告包含可直接复制的下一步命令：

```text
strix --verify --baseline <run-name> --request ./request-after-fix.txt
```

验证报告同时保留完整的原始 Burp 请求，以及每个探针实际发送的变体请求。请求中的 Header、Token、Cookie 和 Body 按原样写入报告，便于直接复制到 Burp Repeater 复现；HTML 页面同样提供完整请求内容，不对这部分内容做自动脱敏。

报告至少包含三段过程证据：

1. 发现入口与推理链：记录从页面、JS 或响应中发现线索的位置，说明提取到的接口或字段，以及如何形成漏洞假设。
2. 接口验证矩阵：列出代表性接口、基线请求、变体请求和结果；接口数量较多时保留代表性样例并说明覆盖范围。
3. Burp Repeater 复现请求：为原始请求和已执行探针提供可复制的 HTTP 请求块，并附预期响应、实际响应摘要和复现说明。

## 请求材料和报告

报告原样保留用户提供和执行器生成的请求材料，以确保复现链路完整。修复复测仍要求用户重新提供修复后的有效请求或认证材料；历史计划用于校验请求结构、目标范围和探针一致性，不要求用户手工编辑计划文件。

Token 限制配置后，TUI 右侧统计区显示“已用 / 限额”；即使尚未产生用量，也显示 `0 / 限额`。本地 HTML viewer 的“用量与费用”区域显示相同的“Token 用量 / 限额”，下载的 HTML 总报告保留 Token 限制与覆盖边界信息。

## 兼容性

- `normal`、`redteam` 和 `--burp-port` 行为保持不变。
- `--verify` 与 `--red`、`--mode redteam`、`--burp-port` 互斥。
- 验证模式不使用普通 Agent/Docker 扫描链路，也不做整站攻击面发现。
- `--baseline` 是验证模式的复测入口；不支持用普通 `--resume` 恢复验证计划。
- 实时 Burp 历史选择暂不纳入首版。

## 验收标准

- Raw HTTP 和 cURL 请求可解析，缺少 Host、Scheme、目标不一致时阻断。
- 计划生成阶段无网络请求，未确认时不能调用执行器。
- 配置 Token 限制后，TUI 和 HTML 页面均显示当前用量与限额；初始用量为零时仍显示限额。
- 六类问题均能完成类型识别和安全策略判断；不满足边界条件时给出阻断原因。
- 第二身份、非幂等请求、SSRF Canary 和文件上传清理边界可验证。
- 报告过程完整保留请求 Header、请求体和可复现响应证据，不对用户明确提供的请求材料做自动脱敏。
- 复测能够区分 `fixed`、`still_vulnerable` 和 `inconclusive`。
- 现有普通模式、红队专项模式和 Burp 被动模式回归测试通过。
