# 101 漏洞验证模式简化设计与实现方案

## 状态

已实现描述驱动的首版核心链路：请求解析、LLM 验证意图、计划确认、受限执行、证据持久化和修复复测比较。CLI 不再按漏洞名称选择固定模板；未生成有效意图时直接阻断并保存失败报告。

## 目标

在现有普通扫描、红队专项模式和 Burp 被动扫描之外，增加一个面向单个漏洞案例的 `verify` 模式。使用者只需要提供：

1. 一个 Burp 请求包（Raw HTTP 或 Copy as cURL）。
2. 一句自然语言漏洞描述。

系统将描述和请求结构交给已配置的 Strix LLM，生成漏洞类型、可变异字段、低副作用探针、对照组和证据判定器，并在发送请求前展示验证计划。LLM 只生成意图，不能直接发请求或调用 Shell。

## 使用方式

交互模式：

```bash
strix --verify
```

交互流程：

1. 粘贴 Burp Raw HTTP 或 Copy as cURL 请求，以单独一行 `__STRIX_END__` 结束。
2. 输入一句问题描述，例如“疑似 IDOR，修改订单 ID 后可能读取其他用户订单”。
3. 查看 Strix 识别的漏洞类型、目标字段、验证动作、预计请求数和副作用提示。
4. 确认后执行；IDOR/BOLA 需要第二身份时，再粘贴第二个请求包。
5. 查看验证结论和报告路径。

自动化或非交互模式：

```bash
strix --verify --request ./burp-request.txt \
  --issue "疑似 IDOR，修改订单 ID 后可能读取其他用户订单" \
  -n --yes
```

修复后复测：

```bash
strix --verify --baseline <历史运行名> \
  --request ./burp-request-after-fix.txt -n --yes
```

请求包中的绝对 URL 会直接确定 Scheme。Raw 请求使用相对路径且没有 Scheme 时，如果同源 `Origin` 或 `Referer` 已明确给出协议则自动采用；否则交互模式只询问一次 `http` 或 `https`，非交互模式直接报错，避免把请求误发到错误协议。

## 输入和内部模型

首版不要求用户填写漏洞类型、参数路径、探针数量、计划哈希或结构化 JSON。内部将输入转换为：

```python
class VerificationCase:
    request: CanonicalRequest
    issue_description: str
    baseline_run: str | None
    supporting_requests: list[CanonicalRequest]
    controlled_canary_url: str | None
```

随后由本地校验器生成 VerificationPlan，包含漏洞类型、目标字段、探针、对照组、断言所需响应摘要、请求上限、计划哈希、计划来源和副作用约束。计划阶段不向目标发送请求；必要的模型调用只处理脱敏请求结构。

VerificationIntent 的模型输出必须通过以下校验才能进入执行器：

- 目标字段必须逐字存在于请求解析器提供的 candidate fields，数组元素使用 body.ids[0] 这类结构化路径。
- 验证能力、动作和判定器采用本地 allow-list；漏洞标签只作为模型返回的报告字段，不参与本地策略分支。载荷限制长度并拒绝数据提取、Shell、读文件和破坏性操作。
- 探针最多 20 个；非幂等请求仍需副作用确认；跨身份、受控地址和 multipart 能力继续执行各自的边界检查。
- 模型调用失败、返回非法 JSON 或无法形成完整意图时阻断，并在报告中记录原因，不退化成猜测执行。
- 响应差异判定支持成对对照和异常响应探针；角色别名会归一化，无法归一化的角色会被标记为未知，不会绕过本地安全边界。可能造成目标负载或不可逆副作用的策略只记录阻断原因，不发送探针。

当前支持的是与漏洞类型无关的验证能力：

| 验证能力 | 作用 | 安全限制 |
|------|----------|----------|
| 字段变异 | 修改请求中已有的 Query、JSON、Form、Header 或 Cookie 字段 | 只能使用 candidate fields，最多 20 个探针 |
| 成对字段变异 | 对同一字段执行两个受控输入并比较响应 | 只比较状态、长度和结构，不执行延时或数据外带 |
| 第二身份对照 | 从第二个授权请求取得同一路径的值 | 没有第二请求或目标主机不一致时阻断 |
| 移除认证 | 在当前请求上移除认证信息后重放 | 只执行有限的认证边界对照 |
| 受控 Canary | 将已有 URL 字段替换为操作员提供的受控地址 | 必须由操作员提供，拒绝本机、内网、云元数据和保留地址 |
| 响应 marker | 检查模型指定的低风险响应标记 | marker 必须由模型明确提供并写入计划 |
| multipart marker | 替换 multipart 内容中的测试标记 | 没有可靠清理动作时默认阻断 |

请求默认保持原始 Host、Scheme 和 Port。第二身份请求也必须使用相同目标主机和端点；不支持跨主机或跨端点替换。

第二身份验证通过 --secondary-request 提供对照请求，执行器会额外记录第二身份控制响应，并要求边界探针与该响应匹配后才允许确认。受控出站能力通过 --canary-url 提供操作员控制的公网地址；模型返回的地址只作为意图信息，不直接发送。

当前版本没有 OOB 回调确认能力，Canary 回显只作为证据不足处理，不单凭回显确认服务端请求伪造。

## 执行边界

所有验证请求由专用 `VerificationExecutor` 执行，不允许 Agent 直接调用 `curl`、Shell 网络命令或任意 MCP 请求。执行器保证：

- 只修改计划识别出的字段。
- 单次计划最多 20 个请求，并在计划中展示预计数量。
- 不自动跟随重定向。
- 不进行暴力破解、批量枚举或批量数据收集。
- POST、PUT、DELETE 等非幂等请求需要额外副作用确认。
- 缺少可靠清理动作的探针被阻断。
- 未确认计划时不调用网络执行器。

`--yes` 只在非交互模式可用，并视为对当前计划及其副作用提示的明确确认；目标范围、计划结构和请求上限仍由执行器强制约束。

## 修复复测和结果

每次验证保存到 `strix_runs/<run-name>/`：

```text
verification-plan.json
verification-result.json
verification-evidence.jsonl
penetration_test_report.md
run.json
```

复测时读取历史计划，校验计划哈希和新请求结构（方法、目标、字段集合和请求体结构一致，认证值和普通参数值可更新），再使用同一组探针和断言执行。结果规则：

- 基线确认、复测未复现：`fixed`
- 基线确认、复测仍复现：`still_vulnerable`
- 基线本身未复现：`inconclusive`
- 任一阶段证据不足：`inconclusive`
- 缺少第二身份：`needs_secondary_identity`

报告包含可直接复制的下一步命令：

```text
strix --verify --baseline <run-name> --request ./request-after-fix.txt
```

验证报告同时保留完整的原始 Burp 请求，以及每个探针实际发送的变体请求。请求中的 Header、Token、Cookie 和 Body 按原样写入报告，便于直接复制到 Burp Repeater 复现；HTML 页面同样提供完整请求内容，不对这部分内容做自动脱敏。确认漏洞时报告单独输出 `可复现 PoC`；未复现、阻断或证据不足时输出 `未复现证明`，列出已执行请求、响应状态、长度、指纹和未满足的判定条件。

报告至少包含三段过程证据：

1. 发现入口与推理链：记录从页面、JS 或响应中发现线索的位置，说明提取到的接口或字段，以及如何形成漏洞假设。
2. 接口验证矩阵：列出代表性接口、基线请求、变体请求和结果；接口数量较多时保留代表性样例并说明覆盖范围。
3. Burp Repeater 复现请求：为原始请求和已执行探针提供可复制的 HTTP 请求块，并附预期响应、实际响应摘要和复现说明。

## 请求材料和报告

报告原样保留用户提供和执行器生成的请求材料，以确保复现链路完整。修复复测仍要求用户重新提供修复后的有效请求或认证材料；历史计划用于校验请求结构、目标范围和探针一致性，不要求用户手工编辑计划文件。

Token 限制配置后，TUI 右侧统计区显示“已用 / 限额”；即使尚未产生用量，也显示 `0 / 限额`。本地 HTML viewer 的“用量与费用”区域显示相同的“Token 用量 / 限额”，下载的 HTML 总报告保留 Token 限制与覆盖边界信息。

## 兼容性

- `normal`、`redteam` 和 `--burp-port` 行为保持不变。
- `--verify` 与 `--red`、`--mode redteam`、`--burp-port` 互斥。
- 验证模式不使用普通 Agent/Docker 扫描链路，也不做整站攻击面发现。
- `--baseline` 是验证模式的复测入口；不支持用普通 `--resume` 恢复验证计划。
- 实时 Burp 历史选择暂不纳入首版。

## 验收标准

- Raw HTTP 和 cURL 请求可解析，缺少 Host、Scheme、目标不一致时阻断。
- 计划生成阶段不向目标发送请求，未确认时不能调用执行器；模型只接收脱敏请求结构。
- 配置 Token 限制后，TUI 和 HTML 页面均显示当前用量与限额；初始用量为零时仍显示限额。
- 六类问题均能由描述驱动完成类型、字段、探针和证据策略生成；不满足边界条件时给出阻断原因。
- 第二身份、非幂等请求、Canary 和文件上传清理边界可验证；没有 OOB 回调时不把 Canary 回显当作出站请求确认。
- 报告过程完整保留请求 Header、请求体和可复现响应证据，不对用户明确提供的请求材料做自动脱敏。
- 复测能够区分 `fixed`、`still_vulnerable` 和 `inconclusive`。
- 现有普通模式、红队专项模式和 Burp 被动模式回归测试通过。
