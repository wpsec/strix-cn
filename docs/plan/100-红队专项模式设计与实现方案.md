# 100 红队专项模式设计与实现方案

## 摘要

本文档记录 Strix “红队专项”模式的设计目标、实现边界和验收标准，供后续代码实现和 Review 参考。

当前实现已接入 `--red`、`--mode redteam`、`STRIX_MODE`、动作风险控制、Prompt 传播、完整报告与攻击链投影以及 TUI/Viewer 模式展示。

红队专项模式只面向已授权目标的受控安全验证。它优先测试可能带来身份、权限或敏感数据影响的问题，同时保留低优先级和未知类型的已观察发现；但不实现 Webshell 投递、反弹 Shell、持久化或真实自动提权。

## 目标

- 在现有 Strix 多代理、沙箱、代理工具和报告链路上增加 `normal/redteam` 运行模式。
- 优先验证可能形成权限获取或高影响攻击链的测试，并记录完整证据以支持后渗透判断。
- 在网络请求发出前依据目标作用域和动作风险拦截越权范围、破坏性、不可逆或不可清理的操作。
- 使用无害、可清理、可审计的 PoC 证明安全影响。
- 红队报告保留全部已观察发现；攻击链仅作为 High/Critical 且证据充分的独立投影。

## 当前架构与落位

实现复用以下现有入口：

| 能力 | 现有位置 | 计划落位 |
|---|---|---|
| 配置 | `strix/config/settings.py` | 增加 `SecurityMode` 和 `mode` 配置 |
| CLI | `strix/interface/cli_args.py` | 增加 `--red`、`--mode` |
| 运行编排 | `strix/core/runner.py` | 传播并持久化模式 |
| Prompt | `strix/agents/prompt.py`、`system_prompt.jinja` | 注入版本化红队策略 |
| 网络工具 | `strix/tools/proxy/`、浏览器和沙箱出口 | 增加请求前策略检查 |
| 报告状态 | `strix/report/state.py` | 保存全部发现并收集攻击链投影 |
| 报告渲染 | `strix/report/writer.py`、viewer | 输出攻击链报告和模式标识 |
| 交互界面 | TUI setup、viewer React | 启动时选择或展示模式 |


## 模式语义

| 行为 | `normal` | `redteam` |
|---|---|---|
| 测试范围 | 按现有扫描策略执行 | 按影响优先级编排，动作风险单独控制 |
| 未知类型 | 按普通模式处理 | 不因分类未知而拒绝安全、在范围内的测试 |
| 验证深度 | 证明漏洞存在即可停止 | 继续到受控影响证明 |
| 文件上传 | 按普通 PoC 策略 | 仅允许随机 marker 文本文件并清理 |
| 云存储 | 按普通 PoC 策略 | 仅允许单个测试对象的未授权读取或 marker 写入，并清理对象 |
| 凭据材料暴露 | 按普通 PoC 策略 | 记录原始材料、来源、验证状态、身份和权限范围 |
| RCE | 按普通 PoC 策略 | 仅允许身份确认类无害命令 |
| 报告 | 漏洞清单 | 全部发现清单 + 已验证 High/Critical 攻击链 |

运行开始后模式不可切换。`--resume` 必须沿用历史运行中的模式。

报告层遵循原生 Strix，不对 `normal` 或 `redteam` 的 Markdown、HTML、JSON 和攻击链证据做字段替换。红队 Markdown、HTML、JSON、CSV 和 SARIF 均保留全部已观察发现；攻击链仅过滤为满足严重度、类型、影响和证据条件的独立视图。SARIF 默认只保留 PoC 描述和脚本存在标记；红队专项 SARIF 额外保留完整复核字段。

## 漏洞策略

### 优先级规则

- 认证绕过、越权/IDOR、默认凭据和会话问题
- 敏感信息访问、注入、文件读写、命令执行和反序列化
- 受控 SSRF 元数据验证、云存储未授权访问或 marker 可写
- 暴露的管理功能、高影响未授权业务操作和可能获得权限的业务逻辑
- 可写文件上传以及有证据支持的凭据材料暴露
- 无效证书、弱 TLS、Banner、缺少安全响应头、普通 CAPTCHA 绕过和低影响限流问题默认延后

CAPTCHA、限流、CORS、CSRF、开放重定向和文件上传等问题一旦影响登录、找回密码、权限变更或敏感数据访问，应立即提升优先级。“可获取到权限”必须由验证结果证明，不能仅凭漏洞名称进入攻击链。云存储和凭据材料问题也必须证明实际访问边界；凭据类证明应完整记录原始值、来源和验证结果。

### 默认延后类别

- 无效证书、SSL/TLS 弱加密
- Banner、缺少安全响应头
- 普通 CAPTCHA 绕过、低影响限流问题
- 普通展示型 XSS、点击劫持和无敏感操作影响的 CSRF

这些类别不是报告黑名单。若证据显示其影响登录、找回密码、权限变更或敏感数据，应提升优先级并正常报告。

### 未知类型

无法可靠归类的类型不因分类缺失而拒绝。编排器可将其作为普通优先级，动作仍须通过作用域、可逆性、清理条件和破坏性检查。已观察到的未知类型必须进入漏洞清单、最终报告和 SARIF；仅因效率跳过的测试记录为未执行项及原因。

## 拦截器设计

`strix/redteam/policy.py` 提供统一类型归一化、优先级判断和动作风险判断：

```python
def classify_test_priority(
    vulnerability_type: object,
    *,
    impact: str | None = None,
) -> dict[str, object]:
    """Return advisory priority metadata; never authorize a request."""

def assess_action_risk(
    method: object,
    url: object,
    *,
    mode: str = "normal",
    body: object = None,
    action_name: object = None,
) -> dict[str, object]:
    """Return whether the target-side action is bounded and non-destructive."""
```

策略需要在以下层级同时生效：

1. AI 或插件生成测试意图时，用于优先级引导。
2. `repeat_request` 和 MCP 网络工具调用时，执行作用域和动作风险检查。
3. 受控 Shell 命令出口处，防止 Agent 通过直接命令绕过工具层。
4. `ReportState.add_vulnerability_report()` 写入报告时，只补充原始类型、规范化类型和优先级元数据，不静默丢弃发现。
5. 红队任务调度按 P0/P1/P2/P3 阶段门控；低优先级任务不能越过未完成的高影响发现和验证阶段。

网络拦截对目标不在授权范围、破坏性或不可清理动作采用 fail-closed；缺失类型或未知类型本身不构成拒绝理由。

## Prompt 设计

红队 Prompt 必须是代码内置、版本化且不可被用户指令覆盖的策略块。它至少应要求：

- 优先测试认证、授权、云存储、凭据和业务逻辑等可能带来权限影响的类别。
- 提醒低优先级检查默认延后，并定义影响登录、权限或敏感数据时的升级条件。
- 只生成最小、无害、可清理的验证动作。
- 不能生成 Webshell、反弹 Shell、凭据导出或复用、持久化、批量收集或真实提权流程。
- 所有发现必须落盘；高危和攻击链结论必须附带可复核证据和反证说明。

Root Agent 和 Child Agent 必须获得同一 `mode` 和策略上下文，避免子代理回退到普通模式。

## 深度验证模块

`strix/redteam/depth.py` 以安全验证控制器替代自动 GetShell：

```python
class RedTeamDepthController:
    async def validate_upload(...): ...
    async def validate_rce_identity(...): ...
    async def validate_sqli(...): ...
    async def validate_ssrf_canary(...): ...
    async def validate_privilege_impact(...): ...
```

约束如下：

- 文件上传只能使用随机命名的无害文本 marker，并在验证后清理。
- RCE 只能执行 `id`、`whoami` 等身份确认动作。
- SQL 注入只能使用无副作用、可回滚的验证查询。
- SSRF 优先访问受控 Canary 或本地测试 Stub，不访问云凭据端点。
- 云存储只使用单个测试对象或随机 marker；凭据材料记录完整获取和验证证据。
- 权限影响只比较授权前后的身份和权限边界。
- 禁止 Webshell、反弹连接、批量凭据收集、凭据自动复用、持久化和自动提权。

## 报告与攻击链

攻击链投影只保留：

- `critical` 或 `high` 严重性。
- 可归类为高影响且满足影响证明的漏洞类型。
- 成功验证的漏洞。
- 至少一份完整、可复核的证据。

攻击链节点应至少包含：

- 漏洞类型、标题和严重性。
- 前后依赖关系。
- 对涉及 HTTP 的节点保留完整 Request/Response；静态或依赖节点明确标记 HTTP 字段不适用。
- 身份或权限证明。
- 时间线、证据引用和清理结果。

节点之间不会仅按时间顺序自动连边。只有报告显式提供
`attack_chain_parent_id` 且该前置节点也满足攻击链证据条件时，才生成
`prerequisite` 关系；无法证明因果关系的节点保持独立展示。

`Authorization`、Cookie、密码、API Key、Token 等字段在授权红队报告中完整保留，不得用占位符替代有效证据。

凭据材料发现必须同时记录来源链：材料类型、原始值、来源载体、具体字段或文件位置、获取动作、验证状态、身份、权限范围、指纹和长度。`validation_status` 至少区分 `observed_unverified` 与 `validated`；缺少受控验证接口时不得把观察结果写成“凭据可用”。红队报告不得用占位符替换原始值。

Markdown 总报告和红队模式下的单漏洞 Markdown 附件统一使用以下固定章节：

1. 漏洞名称
2. 漏洞等级与 CVSS 4.0
3. 漏洞位置：前端功能、后端接口、所属子应用、关键 JS 文件、具体业务功能推测
4. 漏洞描述
5. 漏洞定位过程：前端入口、主壳、微前端、动态模块和业务调用链等客观数据
6. 安全验证过程：请求方法、请求路径、认证状态、Request、Response、影响证明和 PoC
7. 漏洞根因
8. 漏洞影响
9. 修复建议
10. 复测方案
11. 证据限制与待确认事项

报告不得把 CVSS 3.1 分数直接标记为 CVSS 4.0。只有记录中存在真实的 CVSS 4.0 分数或向量时才展示；否则明确标记为未计算，并保留旧版本分数的版本说明。

PoC 只用于授权安全验证，使用 Python 优先；代理地址约定为 `http://127.0.0.1:8080`，代理不可用时允许直连。报告应输出复核所需的完整请求、响应、凭据获取证据和 PoC；不得生成 Webshell、反弹 Shell、批量收集或真实自动提权代码，也不得使用“AI 黑盒测试发现”“通过利用”“绕过”“最终确认利用”等模糊表述，结论应直接引用请求、响应、前端代码和服务端行为。

运行记录至少增加：

```json
{
  "mode": "redteam",
  "policy_version": "redteam-v5"
}
```

## 攻击链报告示例

以下示例只展示无害身份确认，不包含 Webshell、反弹连接或自动提权代码：

````markdown
# 红队专项攻击链报告

## 攻击链路图

### 节点 1：受控命令执行验证

- 类型：`rce`
- 严重性：`HIGH`
- 证据节点：`vuln-0001`
- 权限获取证明：`uid=1000(app) gid=1000(app)`

验证证据：

```text
whoami -> app
```

Request：

```http
POST /authorized-test HTTP/1.1
Content-Type: application/json

{"probe":"identity-proof"}
```

Response：

```http
HTTP/1.1 200 OK
Content-Type: text/plain

app
```

## 节点关系

本次运行只有一个已验证节点。
````

## 目标接口

目标命令行接口：

```bash
strix --red --target https://staging.example.com
strix --mode redteam --target https://staging.example.com
STRIX_MODE=redteam strix --target https://staging.example.com
```

优先级：

```text
CLI 参数 > STRIX_MODE > 持久化配置 > normal
```

引擎调用接口：

```python
await run_strix_scan(
    scan_config={
        "mode": "redteam",
        "targets": authorized_targets,
        "scan_mode": "standard",
        "user_instructions": "优先验证权限影响问题，并仅执行在范围内、无害且可清理的验证。",
    },
    image="strix-sandbox:latest",
)
```

`mode` 不能扩大既有 scope，也不能覆盖系统生成的授权范围。

## 实现验收

- 普通模式行为保持不变。
- `--red`、`--mode redteam` 和 `STRIX_MODE` 能正确选择模式。
- Root Agent 和 Child Agent 使用相同红队策略。
- 低优先级检查被延后时记录原因；未知类型不因分类缺失而拦截。
- 破坏性或越权范围请求不会进入目标服务器；已观察发现不会因类型、严重度或攻击链状态被丢弃。
- 文件 marker、验证 Stub 和测试资源可以清理。
- 红队报告包含全部已观察发现，并单独展示已成功验证的 High/Critical 攻击链。
- 有对应证据时，Request/Response、凭据材料和 PoC 在红队报告中完整可复核；缺失数据必须显示证据缺口或不适用原因。
- `--resume` 不允许改变历史运行模式。
- TUI 和 viewer 能显示当前模式及策略版本。

## 测试计划

至少新增以下测试：

- `normal` 模式回归测试。
- 优先级分类、条件升级和未知类型可测试策略测试。
- 请求传输层的作用域与破坏性动作拦截测试。
- Prompt 模式切换测试。
- CLI、环境变量和 resume 模式一致性测试。
- ReportState 全量落盘、策略元数据和攻击链独立投影测试。
- 攻击链序列化、恢复和完整证据测试。
- marker 文件清理和 SSRF Canary 限制测试。

## 实施状态

1. CLI、环境变量和运行记录已接入模式选择，并在 `--resume` 时锁定历史模式。
2. Runner、Root/Child Agent Prompt、Shell/Proxy/MCP 请求层和 ReportState 已接入红队策略。
3. Markdown、HTML、TUI 和 Viewer 已显示模式、策略版本及攻击链节点。
4. 仍需在 CI 中持续运行针对沙箱出口、插件/MCP 适配器和实际授权测试资源的回归测试。

## 安全边界

仅测试你拥有或已获得明确授权的应用和系统。发现真实高危问题后，应停止扩大验证范围，保留最小必要证据，并按照授权方的事件响应和漏洞披露流程处理。
