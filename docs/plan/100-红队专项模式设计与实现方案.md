# 100 红队专项模式设计与实现方案

## 摘要

本文档记录 Strix “红队专项”模式的设计目标、实现边界和验收标准，供后续代码实现和 Review 参考。

当前实现已接入 `--red`、`--mode redteam`、`STRIX_MODE`、策略拦截、Prompt 传播、报告攻击链以及 TUI/Viewer 模式展示。

红队专项模式只面向已授权目标的高风险漏洞验证，不实现 Webshell 投递、反弹 Shell、凭据窃取、持久化或真实自动提权。

## 目标

- 在现有 Strix 多代理、沙箱、代理工具和报告链路上增加 `normal/redteam` 运行模式。
- 只验证红队专项白名单中的高风险类型。
- 在网络请求发出前拦截黑名单和未知类型。
- 使用无害、可清理、可审计的 PoC 证明安全影响。
- 红队报告以已验证的攻击链表示，不输出中低危或被拦截结果。

## 当前架构与落位

实现复用以下现有入口：

| 能力 | 现有位置 | 计划落位 |
|---|---|---|
| 配置 | `strix/config/settings.py` | 增加 `SecurityMode` 和 `mode` 配置 |
| CLI | `strix/interface/cli_args.py` | 增加 `--red`、`--mode` |
| 运行编排 | `strix/core/runner.py` | 传播并持久化模式 |
| Prompt | `strix/agents/prompt.py`、`system_prompt.jinja` | 注入版本化红队策略 |
| 网络工具 | `strix/tools/proxy/`、浏览器和沙箱出口 | 增加请求前策略检查 |
| 报告状态 | `strix/report/state.py` | 拦截黑名单报告并收集攻击链 |
| 报告渲染 | `strix/report/writer.py`、viewer | 输出攻击链报告和模式标识 |
| 交互界面 | TUI setup、viewer React | 启动时选择或展示模式 |


## 模式语义

| 行为 | `normal` | `redteam` |
|---|---|---|
| 测试范围 | 按现有扫描策略执行 | 只执行专项白名单 |
| 未知类型 | 按普通模式处理 | 默认拒绝 |
| 验证深度 | 证明漏洞存在即可停止 | 继续到受控影响证明 |
| 文件上传 | 按普通 PoC 策略 | 仅允许随机 marker 文本文件并清理 |
| RCE | 按普通 PoC 策略 | 仅允许身份确认类无害命令 |
| 报告 | 漏洞清单 | 已验证 High/Critical 攻击链 |

运行开始后模式不可切换。`--resume` 必须沿用历史运行中的模式。

## 漏洞策略

### 白名单

- RCE
- 可写文件上传
- 堆叠查询 SQL 注入
- 反序列化
- 受控、无凭据读取的 SSRF 元数据验证
- 实际证明产生未授权身份或权限提升的漏洞

“可获取到权限”必须由验证结果证明，不能仅凭漏洞名称放行。账户枚举、信息泄露或权限影响猜测不自动纳入该类别。

### 黑名单

- DOM、反射型和存储型 XSS
- CSRF
- 点击劫持
- SSL/TLS 弱加密
- 路径遍历及其他敏感信息泄露
- 缺少安全响应头

### 未知类型

红队模式对无法可靠归类的类型默认拒绝。拒绝必须发生在请求发出前，并且被拒绝内容不得进入漏洞清单、最终报告或 SARIF。

## 拦截器设计

`strix/redteam/policy.py` 提供统一类型归一化和策略判断：

```python
def should_ignore(
    vuln_type: str,
    *,
    mode: str = "normal",
    impact: str | None = None,
) -> bool:
    """Return whether a finding or test intent must be discarded."""
```

策略需要在以下层级同时生效：

1. AI 或插件生成测试意图时。
2. `repeat_request` 和 MCP 网络工具调用时。
3. 受控 Shell 命令出口处，防止 Agent 通过直接命令绕过工具层。
4. `ReportState.add_vulnerability_report()` 写入报告前。

网络拦截应采用 fail-closed 逻辑：缺失类型、未知类型、策略版本不匹配或目标不在授权范围内，都不得发出请求。

## Prompt 设计

红队 Prompt 必须是代码内置、版本化且不可被用户指令覆盖的策略块。它至少应要求：

- 只测试白名单类型。
- 黑名单和未知类型直接跳过。
- 只生成最小、无害、可清理的验证动作。
- 不能生成 Webshell、反弹 Shell、凭据导出、持久化或真实提权流程。
- 所有高危结论必须附带可复核证据和反证说明。

Root Agent 和 Child Agent 必须获得同一 `mode` 和策略上下文，避免子代理回退到普通模式。

## 深度验证模块

`strix/redteam/depth.py` 以安全验证控制器替代自动 GetShell：

```python
class RedTeamDepthController:
    async def validate_upload(...): ...
    async def validate_rce_identity(...): ...
    async def validate_sqli(...): ...
    async def validate_ssrf_canary(...): ...
    async def validate_privilege_impact(...): ...
```

约束如下：

- 文件上传只能使用随机命名的无害文本 marker，并在验证后清理。
- RCE 只能执行 `id`、`whoami` 等身份确认动作。
- SQL 注入只能使用无副作用、可回滚的验证查询。
- SSRF 优先访问受控 Canary 或本地测试 Stub，不访问云凭据端点。
- 权限影响只比较授权前后的身份和权限边界。
- 禁止 Webshell、反弹连接、凭据读取、持久化和自动提权。

## 报告与攻击链

红队报告只保留：

- `critical` 或 `high` 严重性。
- 白名单漏洞类型。
- 成功验证的漏洞。
- 至少一份完整、脱敏的证据。

攻击链节点应至少包含：

- 漏洞类型、标题和严重性。
- 前后依赖关系。
- 脱敏后的 Request/Response。
- 身份或权限证明。
- 时间线、证据引用和清理结果。

`Authorization`、Cookie、密码、API Key、Token 等字段必须在写入 Markdown、HTML、JSON 或 SARIF 前脱敏并截断。

Markdown 总报告和红队模式下的单漏洞 Markdown 附件统一使用以下固定章节：

1. 漏洞名称
2. 漏洞等级与 CVSS 4.0
3. 漏洞位置：前端功能、后端接口、所属子应用、关键 JS 文件、具体业务功能推测
4. 漏洞描述
5. 漏洞定位过程：前端入口、主壳、微前端、动态模块和业务调用链等客观数据
6. 安全验证过程：请求方法、请求路径、认证状态、Request、Response、影响证明和 PoC
7. 漏洞根因
8. 漏洞影响
9. 修复建议
10. 复测方案
11. 证据限制与待确认事项

报告不得把 CVSS 3.1 分数直接标记为 CVSS 4.0。只有记录中存在真实的 CVSS 4.0 分数或向量时才展示；否则明确标记为未提供，并保留旧版本分数的版本说明。

PoC 只用于授权安全验证，使用 Python 优先；代理地址约定为 `http://127.0.0.1:8080`，代理不可用时允许直连。报告不得输出 Webshell、反弹 Shell、凭据操作或真实自动提权代码，也不得使用“AI 黑盒测试发现”“通过利用”“绕过”“最终确认利用”等模糊表述，结论应直接引用请求、响应、前端代码和服务端行为。

运行记录至少增加：

```json
{
  "mode": "redteam",
  "policy_version": "redteam-v1"
}
```

## 攻击链报告示例

以下示例只展示无害身份确认和脱敏数据，不包含 Webshell、反弹连接或凭据内容：

````markdown
# 红队专项攻击链报告

## 攻击链路图

### 节点 1：受控命令执行验证

- 类型：`rce`
- 严重性：`HIGH`
- 证据节点：`vuln-0001`
- 权限获取证明：`uid=1000(app) gid=1000(app)`

验证证据：

```text
whoami -> app
```

Request（已脱敏）：

```http
POST /authorized-test HTTP/1.1
Content-Type: application/json

{"probe":"identity-proof"}
```

Response（已脱敏）：

```http
HTTP/1.1 200 OK
Content-Type: text/plain

app
```

## 节点关系

本次运行只有一个已验证节点。
````

## 目标接口

目标命令行接口：

```bash
strix --red --target https://staging.example.com
strix --mode redteam --target https://staging.example.com
STRIX_MODE=redteam strix --target https://staging.example.com
```

优先级：

```text
CLI 参数 > STRIX_MODE > 持久化配置 > normal
```

引擎调用接口：

```python
await run_strix_scan(
    scan_config={
        "mode": "redteam",
        "targets": authorized_targets,
        "scan_mode": "standard",
        "user_instructions": "仅执行红队专项白名单中的无害验证。",
    },
    image="strix-sandbox:latest",
)
```

`mode` 不能扩大既有 scope，也不能覆盖系统生成的授权范围。

## 实现验收

- 普通模式行为保持不变。
- `--red`、`--mode redteam` 和 `STRIX_MODE` 能正确选择模式。
- Root Agent 和 Child Agent 使用相同红队策略。
- 黑名单和未知类型在请求传输前被拦截。
- 被拦截请求不会进入目标服务器、漏洞报告、HTML、Markdown 或 SARIF。
- 文件 marker、验证 Stub 和测试资源可以清理。
- 红队报告只包含已成功验证的 High/Critical 攻击链。
- Request/Response 中的敏感字段正确脱敏。
- `--resume` 不允许改变历史运行模式。
- TUI 和 viewer 能显示当前模式及策略版本。

## 测试计划

至少新增以下测试：

- `normal` 模式回归测试。
- 白名单、黑名单和未知类型策略测试。
- 请求传输层未被黑名单意图调用的测试。
- Prompt 模式切换测试。
- CLI、环境变量和 resume 模式一致性测试。
- ReportState 和报告渲染过滤测试。
- 攻击链序列化、恢复和脱敏测试。
- marker 文件清理和 SSRF Canary 限制测试。

## 实施状态

1. CLI、环境变量和运行记录已接入模式选择，并在 `--resume` 时锁定历史模式。
2. Runner、Root/Child Agent Prompt、Shell/Proxy/MCP 请求层和 ReportState 已接入红队策略。
3. Markdown、HTML、TUI 和 Viewer 已显示模式、策略版本及攻击链节点。
4. 仍需在 CI 中持续运行针对沙箱出口、插件/MCP 适配器和实际授权测试资源的回归测试。

## 安全边界

仅测试你拥有或已获得明确授权的应用和系统。发现真实高危问题后，应停止扩大验证范围，保留最小必要证据，并按照授权方的事件响应和漏洞披露流程处理。
